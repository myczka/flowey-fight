# Design Notes

The reasoning behind `REFACTOR_PLAN.md`, collected from the first planning sessions (October 2026). The plan says *what* to do; this file says *why*, and lists the sources found.

## 1. Modularizing: the core idea
- Split code by **reason to change**, not just into more files. The original `flowey.cpp` mixed five concerns: state/data (globals), rules (damage, AI), presentation (typewriter, sounds, timing), content (dialogue, spell names) and flow control (`main` plus `goto`).
- C++ enforces module boundaries through the **compiler and linker**, not folders: headers declare, `.cpp` files define. A function body in a header compiles fine with one `.cpp` and breaks with "multiple definition" errors once two `.cpp` files include it.
- Single-header libraries (miniaudio, stb, nlohmann/json) need their implementation switch (`MINIAUDIO_IMPLEMENTATION`) defined in exactly one `.cpp`. A dedicated `miniaudio_impl.cpp` also keeps the ~95k lines from recompiling whenever `main.cpp` changes.
- Draw the include arrows: dependencies point down (game → engine → third-party), siblings don't point at each other, nothing points back up. A sideways arrow usually means a function is in the wrong module (for example, `getRand` belonged in `util`, not `console`).

## 2. Standard patterns (all map to Unity/Unreal concepts)
1. **Game loop with a top-level owner** (`Game::run()`); `main` stays thin.
2. **State / scene machine:** Intro, NameEntry, Battle, Ending. The old `goto fight_start` was a hand-written state machine.
3. **Entities as data:** a `Combatant` (the user also calls it Character) struct instead of loose `health`/`flowey`/`mana` globals.
4. **Managers / systems:** one object owns one subsystem behind a few verbs (`AudioManager`, `BattleManager`). They exist to hide a messy subsystem, not as a goal.
5. **Data-driven design:** spells, attacks and items as tables, with one generic function interpreting them.
6. **Command pattern:** turn actions as objects with `execute()`.
7. **Pass dependencies in** rather than using globals; singletons and service locators are the quick-and-dirty version.
- Not now: ECS (solves performance problems this game doesn't have) and event buses (useful later for decoupling).

## 3. Project layout conventions
- For an application, keep headers next to their `.cpp` in `src/` and group by area (`src/engine`, `src/game`). A separate `include/` folder is a **library** convention for public headers; it can be adopted later if the engine becomes a reusable library.
- Third-party code goes in a root `third-party/` (or `external/`/`vendor/`), marked `SYSTEM` in CMake so its warnings stay quiet.
- **pokeemerald comparison:** its `src/`, `include/`, `asm/`, `data/`, linker scripts and `rom.sha1` come from being a C decompilation that must rebuild a GBA ROM bit for bit. The ideas overlap (its tasks/callbacks are a C-era state machine, its `data/` is data-driven design) but its constraints don't apply here. No single "industry layout" exists; Unity (`Assets/Scripts`), Unreal (`Source/<Module>/Public|Private`) and studios all differ.
- `lib/cppLibrary` used to be a git subtree of the separate cppLibrary repo; after the history reset it became plain files and was folded into `src/engine` and `third-party`. A library earns its own repo once it is stable, game-agnostic and used by a second project.

## 4. Menu tree design
- A menu is a **general (n-ary) tree**: each node has a label and a vector of children; a node with no children is a **leaf**. Binary trees, BSTs, heaps and tries are the wrong structure.
- Leaves hold a `std::function<void()>` action, which replaces the index arithmetic (`bMenuSize - 3`) and `goto start_turn`. This is the **Composite pattern**.
- **Separate data from navigation:** a plain-data `MenuNode`, plus a navigator/`MenuTree` that owns the current node, a stack of ancestors (for X/back), the cursor index and `select()`. The current `Menu` class should not be the node: it owns an `ma_engine` per instance (not copy-safe, and one audio device per menu), and it owns input, rendering and cursor state that belong to the single active menu. Reuse its `display`/`readKey` code inside the navigator.
- Dynamic submenus (items, spells by mana) can be generated by a callback each time they open. Beware `[&]` lambda captures outliving what they capture.
- Start non-template; add a payload template parameter only when a real need appears.
- Storage alternatives, as later data-structure exercises behind the same interface: first-child/next-sibling links, a flat arena of nodes with integer indices (cache-friendly, common in engines), small-buffer vectors (`llvm::SmallVector`). For a ~20-node menu, `std::vector` is the right production choice. Writing a `MyVector<T>` separately is a good C++ exercise (rule of five, placement new, growth).
- Dialogue with choices is the same kind of tree, so one tree type could serve both.

## 5. Text, voices and audio
- **`Voice`** (file or blips plus delay) is data; **`Speaker`** is the mechanism that types text with a borrowed engine. The engine type is generic; the specific voices (Flowey, Wolfey, Chara, narrator) are game data.
- It is one Speaker per audio channel, not per combatant: Flowey has two voices, the narrator and HP-tick sounds belong to nobody. Combatants may hold a `Voice` or a pointer to one; the Speaker must never know about combatants.
- Voices should be constructed after audio is initialized, not as globals across files (the static initialization order problem).
- `voiceEng` and `buffVoiceEng` exist only to give two volume levels. The proper tool is one `ma_engine` plus `ma_sound_group`s per channel (music, effects, voice, loudVoice), verified present in the repo's `miniaudio.h`. Each `ma_engine` opens an audio device.
- `ma_sound_set_at_end` is a private (`static`) miniaudio function; only `MA_API` functions in the upper part of `miniaudio.h` are public.
- Typing-timing accuracy: per-character `playSound` reloads the file (fixed by preloading); `sleep_for` only guarantees *at least* the duration (OS timer resolution can be ~1 to ~15 ms); errors accumulate (fixed by `sleep_until` against a schedule); flush `std::cout` after each character.
- `getRand` keeps one `static thread_local std::mt19937` seeded once from `std::random_device`; `getRand(a, b)` includes both ends and requires `a <= b`. Deterministic replays (Touhou-style) would need a seedable, owned generator.

### AudioManager design (October 24 session)
- **Preload every sound, including sfx and text blips** (user decision). `ma_engine_play_sound` is fire-and-forget: each call creates a new internal sound and loads the file, so fast text stacks overlapping blips (`miniaudio.h` lines 1190-1197). One owned `ma_sound` per blip, restarted with seek-to-0 plus start (the existing `begin()`), cuts off the previous blip the way Undertale does, and the file is loaded only once.
- Load short sfx and blips with `MA_SOUND_FLAG_DECODE` (decoded into memory at load time, cheap to play; `miniaudio.h` lines 406-412). Keep `MA_SOUND_FLAG_STREAM`, which `initSound` uses for everything today, for long music.
- Tradeoff: one `ma_sound` can't overlap itself. That is the goal for blips; if a sound ever needs to overlap (rapid hits), keep a small pool of copies (`ma_sound_init_copy`). miniaudio's resource manager shares decoded data between sounds loaded from the same path, so copies don't reload the file.
- **Every `ma_sound` and `ma_sound_group` is a node in the engine's graph and must not move after init** (the engine holds pointers to it; general knowledge, consistent with the node-graph description at `miniaudio.h` lines 424-426). Consequences:
  - `std::vector<ma_sound>` is unsafe because growth relocates elements (general knowledge). Use `std::vector<std::unique_ptr<ma_sound>>`: the pointers move, the sounds don't.
  - `std::unordered_map` keeps references to its elements valid across rehashing (only erasing that element invalidates them), so a map also works ([cppreference](https://en.cppreference.com/cpp/container/unordered_map)); `unique_ptr` still makes the "must not move" rule visible.
  - Groups are a fixed set, so `std::array<ma_sound_group, static_cast<std::size_t>(Group::Count)>` as a member is fine: an array never resizes, and AudioManager itself is non-copyable and non-movable.
- **Naming sounds.** miniaudio has no public sound ID: an `ma_sound` is identified by its address. (Its resource manager hashes file paths internally, `miniaudio.h` line 10434, but that is a cache key for audio data, not a handle.) Options discussed:
  1. `load(file, group)` returns a `SoundId` (vector index wrapped in a struct so a random `int` can't be passed), and the game keeps the IDs in a struct of named fields (`sounds.slash`). Fast, compile-time-checked names, engine stays generic. Recommended. Unreal's sound handle system works the same way: create the sound, return an ID, play and stop through the ID ([ISoundHandleSystem](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/ISoundHandleSystem)).
  2. A string-keyed map (`soundMap` in the current header). Simplest, but typos fail at runtime.
  - Rejected: an `enum` of sounds in `engine/` (puts the game's sound list in the engine, the same mistake as `extern audioDir`), and a game-side enum that must match load order (silently plays the wrong sound if the orders drift).
  - Speed is not the deciding factor: a string hash is far below a microsecond, and each typed character waits 30-50 ms.
  - **Still open:** the user has not chosen between 1 and 2.
- **Groups:** an `enum class Group { Music, Sfx, Voice, Count }` nested in `AudioManager` (a global `Group` name is likely to clash). Music, sfx and voice are generic categories, so they may live in the engine. `loudVoice` is game-specific and is only voice at volume 1.2 (`main.cpp` line ~505), so it can be voice sounds with per-sound volume 1.2 instead of its own group. Sound volume and group volume multiply. This is an alternative to the four-group list in section 5 above, not yet decided.
- **Lifetime:** RAII. The constructor (or `init`) creates the engine, then the groups; the destructor uninitializes sounds, then groups, then the engine (children before parents). Delete copy *and* move: copying an `ma_engine` would uninitialize it twice, and moving would leave Speaker's reference dangling.
- **Failure without exceptions:** a constructor can't return an error, so use `bool init()` (simple, but can be forgotten) or a private constructor plus a static `create()` returning `std::unique_ptr` (empty on failure). On failure, keep running muted (a flag that turns play calls into no-ops) instead of today's print-and-continue in `init()` or silent `exit(0)` in `initSound()`.
- `ma_engine_init(NULL, &engine)` creates its own context and default playback device, which the docs call sufficient for many uses (`miniaudio.h` lines 1050-1052). `ma_engine_config` is only needed to change defaults (sample rate, `pPlaybackDeviceID`, `noAutoStart`); `ma_context` only to enumerate devices (for an output-device setting); `ma_device` only for a hand-written audio callback.
- **Per-sound control** is complete with owned sounds (all `MA_API` in the repo's header): volume, pan, pitch, start/stop, seek, `ma_data_source_set_range_in_pcm_frames` (start and end points), `ma_data_source_set_loop_point_in_pcm_frames` (intro plus looping section), fades, scheduled start/stop times and `ma_sound_set_end_callback`. The range and loop functions take `ma_sound_get_data_source(&sound)`. Settings persist between plays, so per-line pitch must be set before each play. Expose everyday wrappers plus a `get(id)` escape hatch.
- Classes vs structs: a **class** when it owns resources or protects rules (AudioManager, Speaker); a **struct** for plain data (`Voice`, `Spell`, `Segment`).

### Speaker, Voice and characters
- **Speaker holds `AudioManager&`**, not an engine. Its two instances (`buffVoice`, `theVoice`) exist only because there are two engines; once each `Voice` names its sounds (and their group), one Speaker can serve everyone. Construct `AudioManager` before `Speaker` so it is destroyed after it. (R5 says "Speaker then holds a group pointer"; holding the manager is the alternative discussed here. Not decided.)
- **`Voice { std::vector<SoundId> blips; int delayMs; }`**, not `{ ma_sound&, int }`: a reference member makes `Voice` unassignable and puts miniaudio types into game code. A normal voice is a vector of one; Mettaton's random blips are several.
- **The four `write`/`writeRand` variants are one loop:** each is "for each character, pick a voice from a list, play it, wait". One voice is a list of one; a fixed `time` overrides the delay. Merge them into one private core loop (step R1/Speaker cleanup) before adding tags, or the tags have to be written four times.
- **Character == Combatant** (the user uses both names). If `say()` lives on the character, pass the Speaker in (`flowey.say(speaker, "Howdy!")`) rather than storing `Speaker&` in every character: a reference member makes the struct unassignable and prevents building characters from data tables; a global Speaker is the same hidden dependency as `extern audioDir`. With the frame loop, `say` will queue a line on the typewriter instead of printing, and a passed-in Speaker keeps that change local.

## 6. Dialogue conventions
- Typical systems have three layers: **presentation** (typewriter, blips, wrap, advance prompt), **data** (lines with speaker, text, pause, choices, conditions, events) and **flow** (a runner over a tree/graph of nodes).
- Content lives in data files keyed by ID; code only triggers it (`startDialogue("intro_chara")`). Keeping text out of code is also what makes localization possible.
- Engines: Unity commonly uses Yarn Spinner, Ink or Dialogue System plugins with ScriptableObjects and Localization string tables; Unreal uses Data Tables, String Tables, Data Assets or dialogue-graph plugins. Large studios typically build in-house graph editors over similar data (internals of specific games were not verified).
- Inline pause tags (`|500|`) parsed into segments are the format the external file will use.

### Pause tags: implementation notes (October 23-24 sessions)
- **Order of work:** finish the Speaker merge first (a refactor, behavior unchanged), then add tags as a separate change. Mixing a refactor and a feature hides which one caused a bug. The first attempt also showed why: the tag code was only in the 2-argument `write`, but `chara()` calls the 3-argument one.
- **Parse first, then render:** `parse(const std::string&) -> std::vector<Segment>` (`Text` or `Pause{ms}`) with no audio or printing, so it can be tested alone (`"hi|500|there"`, `"||"`, `"|5o0|"`, `"oops|"`). Rendering walks segments; a `Pause` sleeps now and adds to the typewriter timer after the frame loop. The same segments carry over unchanged.
- **Scanning:** on `|`, `find('|', i + 1)` for the closing pipe, convert the digits between them, then skip past it. No `parsing` flag or per-character buffer, so no state leaks between tags.
- **Converting without exceptions:** `std::from_chars` (`<charconv>`, C++17) is non-throwing, non-allocating and locale-independent, and reads straight from `mssg.data()` without a `substr` ([cppreference](https://en.cppreference.com/cpp/utility/from_chars)). A tag is valid only if `ec == std::errc{}` (no match gives `invalid_argument`, too large gives `result_out_of_range`), `ptr` reached the closing pipe (otherwise `|50x|` would read as 50), and the value is in range (for example 0 to 5000 ms).
- **Failure policy:** a malformed or unclosed tag is printed literally, so it shows up in playtesting. Alternative: assert in debug, skip in release. With external dialogue files, a load-time validation pass can catch these before the player sees them.
- **Bugs found in the first attempt:** the generic `!= ' '` check came before the `'|'` check, so tag branches never ran (test special characters before generic ones); tag characters were still printed, voiced and timed (handle them, then `continue`); the parsed value was never used; the buffer was never cleared between tags; `int parsed` was uninitialized.
- **`wrap()` must count visible characters.** It decides line breaks from the raw index `i` and reads `yeet[i - 1]` and `yeet[0]` (`console.cpp` line 12), so tag characters shift wrapping. Track a visible-character count, the previous printed character and "starts with `*`" across segments instead.
- **Blocking `sleep` is acceptable until the frame loop** (R9): the game is turn-based and already timed by `sleep`. It becomes wrong once anything must keep happening while text prints (skip key, animation, input during attacks).

## 7. C++ details from code reviews
- **File names:** C++ has no official rule; consistency matters. snake_case (`audio_manager.h`) matches the standard library, Boost and Google style and fits this repo's lowercase files; the class inside stays PascalCase (`AudioManager`). Every module is a `.h`/`.cpp` pair (a file with no extension was created by mistake once) and each new `.cpp` goes in `add_executable`.
- **Enums:** `enum class Group { ... } const groups;` declares a *variable* after the closing brace (and a `const` one with no initializer, a compile error). End the enum with `};`. Values are reached with `Group::Count`, not `.`; `enum class` does not convert to an integer, so array sizes and indexes need `static_cast<std::size_t>` (put it in one helper).
- **Enumerator names:** avoid ALL_CAPS (`MUSIC`, `COUNT`). That is the macro convention, and any header (including Windows headers) defining a macro with the same name breaks the enum with a confusing error. Use `Music`, `Count`.
- **Reference members** (`Speaker&`, `ma_sound&`) make a class unassignable; prefer passing references into calls, handles, or pointers when the object must be copied or reassigned.

## 8. Custom engines vs commercial engines
A purpose-built engine reused across games (as ZUN reportedly does for Touhou, from general knowledge) is the direction this project points. Missing pieces for a real-time game: a fixed-timestep loop, a window and rendering (DirectX/OpenGL, or SDL/raylib/SFML as the platform layer), per-frame input polling, object pooling, and deterministic RNG for replays. Commercial engines' "bloat" is mostly tooling (editors, pipelines, ports, physics); a custom engine is leaner for a narrow genre but you build or skip each of those yourself.
